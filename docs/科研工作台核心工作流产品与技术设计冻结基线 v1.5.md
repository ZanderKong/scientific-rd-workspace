# 科研工作台核心工作流产品与技术设计冻结基线 v1.5

日期：2026-09-05。审查代码基线：`main@93700a6`。

本文合并 v1.3 产品方案、v1.4 源码审查与用户对 v1.4 的回应，作为下一阶段设计的唯一入口。**产品语义与领域边界固定；Inline PropertySlot 的具体实现需通过原型门禁。** 本文不是 Coding Plan，不表示功能已经实现。

`docs/current/`、CURRENT_STATE 与现行代码仍描述 v0.3 运行契约。v1.3、v1.4 保留为设计历史和证据；与本文冲突时，未来设计以本文为准。尤其不再沿用 v1.4 中“ProcessRef 默认只是 mention”“文档顺序不能形成执行顺序”“属性弹出编辑为默认体验”“首版提供空实验创建入口”的建议。

## 1. 本轮结论与固定原则

接受用户的核心修订。`/Process` 是明确记录一次实际执行的入口，这一产品语义不应被当前代码形态改变。它与“Object 不自动属于最近 Process”完全可以同时成立。

固定以下原则：

1. Scientific Composer 记录实际科研过程；新输入尚在草稿时是待提交的记录，保存后才成为服务端科研事实。
2. 每个可编辑 ProcessOccurrence 对应一个 ProcessExecution，不需要用户再去另一个页面创建执行。
3. `@Object` 明确本次记录中的对象出现及其使用属性；不自动声明它被哪个 Process 使用、消耗或产出。
4. Sample 制备记录、Data 获取记录内的 Process 相对顺序，是该记录声明的流程顺序，保存时同步受该记录管理的 `precedes`。
5. Object 的位置、普通段落、标题与换行不推导 binding；最后一个 Process 也不自动成为 Sample/Data 的 producer。
6. Process 实际值与明确 bindings 由 Execution 持有；文档持有写作结构和顺序；查询 projection 没有独立写权限。
7. 一个 Execution 只有一个可编辑记录来源。重复展示同一次执行使用只读固定版本引用，不产生第二个可编辑 ProcessOccurrence。
8. PropertySlot 第一目标仍是正文内直接编辑、Tab 连续填写。紧邻属性编辑器只是原型失败后的 fallback。
9. Sample、Data 都允许没有 Process；Data subject 可来自显式声明，不制造虚拟执行。
10. 延续 PostgreSQL、现有七种 kind、现有领域服务与 REST/MCP 共用模型。在现有代码上重构，不写第二套工作台。

这里的“实际发生”是用户对科研记录的明确声明，不代表系统通过传感器验证了事件发生；也不代表系统知道准确发生时间或该过程已完成。`recorded_at` 与实际 `occurred_at/started_at/completed_at` 分开，缺失的实际时间不能填成保存时间。

首次正常保存一个新 Process 时，默认标为“已记录发生，完成情况未说明”（recorded）；只有用户明确声明运行中/已完成时使用 running/completed。记录草稿状态、实际执行状态与记录撤回状态分开，不强迫用户填写准确时间。

## 2. 权威数据分配：解决文档与 Execution 双写

### 2.1 唯一权威不是只能有一张表

一次完整记录由多个各司其职的实体组成，但每个字段只有一个权威拥有者。

| 数据 | 权威拥有者 | 其他位置的性质 |
| --- | --- | --- |
| 段落、Text、Ref 位置、Process 顺序 | ScientificDocument | ordinal/sequence edge 是投影 |
| Process Definition/Version、实际参数、执行状态 | ProcessExecution | editor 草稿是待提交编辑；历史文档含固定版本引用 |
| Process 的明确 Object/Data bindings | Execution binding | 文档标记/表格值是展示投影 |
| 尚未绑定 Process 的 ObjectOccurrence 属性 | 文档 ObjectOccurrence | occurrence table 是投影 |
| 已绑定 ObjectOccurrence 的本次使用值 | 对应 Execution binding | inline 展示与历史快照不独立修改 |
| 当前表格 occurrence 索引 | 无独立权威 | 从文档、Execution 与 binding 同事务重建 |
| 实验成员 | Experiment references | Table scope/计数是读模型 |
| 历史事实 | 不可变 ObjectRevision/ExecutionRevision 等 | 只通过新 revision 更正，不改历史 |

不采用“把所有字段 JSON 同时保存在正文和 Execution，再双向同步”。前端看起来仍是一份连续文档，后端按权威分解持久化。

### 2.2 概念模型

```text
ScientificDocument（使用现有 owner 的 content_document，增加格式版本）
  owner: Sample ResearchObject | Data
  blocks[]
    Text
    ProcessOccurrence { occurrence_id, execution_id }
    ObjectOccurrence
      occurrence_id
      target_object_id / target_object_revision_id
      field snapshot + values             # 未绑定时
      binding_ref?                        # 绑定时替代可编辑 values

ProcessExecution
  execution_id
  authoring_record_id?                    # 唯一编辑归属，不是产物 ownership
  authoring_occurrence_id?
  definition_id / definition_version_id
  actual_values / field_snapshot
  execution_status
  record_validity: active | retracted
  object_bindings[] / data_bindings[]
  revisions[]

ObjectRevision（Sample/Data 记录版本）
  document structure
  execution_manifest[]: execution_id + execution_revision_id
  binding refs 可通过对应 ExecutionRevision 定位
  sequence snapshot
  Data 时还包含 representations / subject / provenance manifest

document_occurrences（只读当前投影）
  owner_id / owner_revision_id
  occurrence_id / kind / ordinal
  target_id
  execution_id? / binding_id?
  field identities + values / role
```

一个 ProcessOccurrence 即一次执行在其编辑记录中的位置。不同 ProcessOccurrence 即使指向同一个 Definition，也产生不同 execution ID。用户复制一段文字不会复用原 execution ID。

`authoring_record_id` 只约束谁能修改执行和顺序；不会使删除 Sample/Data 级联删除它。一个执行仍可以明确产出多个 Sample/Data；这些输出对象不因此共同拥有编辑权。

直接 API 创建、尚未归属文档的 Execution 可以独立存在。纳入可编辑文档需原子设置唯一 authoring record；不能静默抢占另一个文档的执行。

### 2.3 当前读取与历史读取

当前编辑器一次性读取 document + 对应 Execution/binding 值，生成适合编辑的 enriched DTO。不能为每个 chip 各发一个请求。

持久化文档 Process 节点不另存一套可写的实际参数。显示用快照允许存在于不可变 revision 或只读响应，必须标明源 execution revision。

旧 ObjectRevision 始终沿其 execution manifest 读取旧值；不从 Execution 当前行取值补进旧记录。因此今天把 60 ℃ 更正成 80 ℃，昨天的记录版本仍显示 60 ℃。

### 2.4 两种方案比较

| 方案 | 数据一致性 | 实现成本 | 结论 |
| --- | --- | --- | --- |
| A：文档保存全部实际值，Execution 全部作为投影 | 可实现，但必须禁止所有 Execution 独立写入，现有外部执行能力也要改成文档优先 | 表面保存简单，迁移与 API 适配范围大 | 不选 |
| B：Execution/Binding 保存实际值；文档保存结构；聚合命令统一提交 | 各字段一个权威，可保留 Execution 领域能力；需明确编辑归属与版本 | 聚合命令和草稿 codec 有成本，长期依赖更清楚 | **采用** |

方案 B 不要求两个独立 Save 按钮，也不引入第二套全局状态。服务器的字段拥有者和用户看到的编辑界面可以不同。

## 3. Editor 草稿、保存、Undo 与并发

### 3.1 草稿是未提交的编辑，不是第二份已生效事实

进入编辑器时保留 base record revision。BlockNote 中的 Process 节点可以暂存实际参数 draft payload，用来原位输入、复制和撤销；保存 codec 将其转换为 Execution mutations，数据库文档节点最终只保存稳定引用。

原子节点 props 只支持基础类型时，可以使用带版本的 JSON payload 字符串承载编辑草稿。API 对外仍是类型明确的结构，不要求 Agent 操作 BlockNote JSON 字符串。

持久化本地草稿包含 base revision、文档与待提交值。恢复后先检测服务端版本；不建立离线自动写入或自动合并机制。File 恢复能力与文本恢复分别处理。

### 3.2 一个 record command 完成全部保存

概念输入：

```text
save_scientific_record
  owner_id? / project_scope_id
  expected_record_revision
  document_draft
  execution_drafts keyed by occurrence_id
  explicit_binding_mutations
  idempotency_key
```

服务器处理要求：

1. 校验请求大小、文档格式、scope、稳定 IDs 和每个 Process 的模板版本。
2. 锁定编辑记录和受影响的 Execution；多对象按稳定顺序加锁，再检查版本。
3. 按 `(authoring_record_id, occurrence_id)` 解析现有 execution；新 occurrence 分配新的 execution ID。映射本身受唯一约束保护，不能依赖可重建的投影表保存身份。
4. 保存 Process 实际值和明确 bindings；未提交的字段不被默认空集合覆盖。
5. 校验新增/删除/重排操作，在最终预期图上检查循环和依赖冲突。
6. 更新文档管理的 sequence edges，生成发生变化的 ExecutionRevision。
7. 保存 canonical document 与其 execution manifest，生成 owner ObjectRevision，再更新 occurrence/subject 等投影。
8. 业务结果、revision、幂等 replay 记录以及 ChangeSet applied 状态（如适用）一次 commit。

Data 文件上传不在该 SQL 事务内；Data finalize 在文件已准备后复用相同文档/执行保存逻辑。任何校验失败都不能只保存正文却漏掉 Execution。

### 3.3 唯一写入口包括 REST/MCP

文档管理的 Execution 不允许通过低层 PUT 独立改完后等待文档追赶。现有 Execution API 应根据 authoring record 转入同一聚合命令；外部客户端需要带期望记录版本，缺失时返回明确错误与操作入口。

没有 authoring record 的 Execution 继续走独立命令。MCP 调用同一 canonical service，不复制转换和同步代码。Graph edge、occurrence projection 和 binding projection 不暴露独立科学事实写入口。

### 3.4 Undo/Redo 与保存中的编辑

- 插入、字段修改、替换、binding 选择和重排必须参与同一个编辑历史；不能让属性输入有一个与正文脱节的长期 undo 栈。
- 保存前撤销插入，不创建服务器 Execution。
- 保存前删除再撤销，恢复原 occurrence/execution 身份，不生成重复执行。
- 保存之后 Undo 是一份新的待提交更正；再次保存生成新 revision，不回滚已发布历史。
- 服务器身份回填不能清空 undo 历史。即使旧 undo frame 没有服务器 execution ID，也能用稳定 occurrence 映射解析到同一次执行。
- 每次保存针对固定 draft generation。期间继续编辑的内容属于下一代草稿，响应不得把它覆盖成旧内容；若原型尚不支持这种行为，可短暂锁定保存期间的编辑，不能静默丢字。
- Query refetch 不初始化 dirty editor。记录冲突保留草稿，提供具体更改位置；首版不自动合并实际参数或执行顺序。

## 4. Process 顺序与 `precedes`

### 4.1 接受自动同步，但限定权威范围

文档内按确定的阅读顺序抽取可编辑 ProcessOccurrences：`P1, P2, P3`。保存时声明本记录的默认流程顺序：`E1 → E2 → E3`。正文换行、Object 顺序或无 Process 段落移动不影响它。

这表示**用户记录的流程先后**。它不自动说明 P1 结束时刻早于 P2 开始时刻，也不证明两者有 input/output 因果关系。若将来支持并行/循环流程，需增加明确模型；首版不通过排版或时间猜测并行关系。

用户移动 Process 时，当前草稿流程顺序立即改变；保存时与 Execution revisions 原子生效。普通重排不逐次弹确认，可在保存差异中显示“流程顺序已调整”。

### 4.2 对 sequence edge 标记来源

推荐在现有 execution relation 上区分 `source=record_sequence` 与 `source=explicit`，为 record_sequence 标明 authoring record。可以用关系行自身的来源字段，也可用小型来源记录；同一对节点同时有两个依据时必须保留两个依据。

文档只撤销/重建自己产生的边，不能删除外部显式关系。查询有效 `precedes` 时对相同 source/target 去重。

| 方案 | 一致性 | 复杂度 | 结论 |
| --- | --- | --- | --- |
| A：只保存文档顺序，不生成 edge | 简单，但 Execution API/Graph 看到的流程会缺失 | 低 | 不符合本次产品要求 |
| B：保存带来源的 record_sequence 投影 | 文档与执行图一致，可保护显式关系 | 中 | **采用** |

不能简单复用当前“删除所有节点之间的 precedes，再重建”的代码。重排 cycle check 要针对“移除本记录旧投影、加入预期新投影”后的最终图，不能先检查旧图而误判反转为循环。

如果新顺序与已有外部关系形成环，整个保存返回具体冲突；保留本地草稿，不选择性忽略一条边。其他文档只能只读展示这些执行，防止两份文档竞争定义同一组执行的顺序。

Object bindings 仍完全独立。尤其不能因为 E3 最后出现，就把当前 Sample 或 Data 自动设成 E3 的 output。

## 5. ObjectOccurrence 与最轻量的明确 binding

### 5.1 不强迫填 binding，保留准确的语义层级

一份记录可包含真实 Process 和未分配 Process 的对象使用记录。这不是错误，也不要求用户补全才能保存。系统能知道“记录了搅拌、记录了乙醇用量”，但只有明确关联后才能回答“该用量用于这次搅拌”。

候选 tag 可以建议角色，不能直接成为最终 input/context/output。角色与方向分别保存；例如 subject 是用途语义，测量 subject 通常对应 input，equipment 通常对应 context。

### 5.2 使用当前 Ref 的轻量关联菜单

选中 ObjectRef 后提供“关联过程”：

```text
关联过程：不关联 / 搅拌① / 浸渍① / 搅拌②
本次用途：投入物 / 测试对象 / 使用设备 / 产物 / 其他
```

用户点击选择即记录明确 binding，不增加 StepBlock、常驻 Process Card 或独立表单页面。选中 ProcessRef 也可打开同一菜单，选择本记录已有 ObjectOccurrences；两种入口使用同一命令。

仅在展开关联菜单时显示方向/角色。允许 API 传精确组合；UI 用常用用途映射到 direction+role，并在需要时编辑。

**首版一个 ObjectOccurrence 表示一次使用记录，最多关联一个可编辑 Process binding。** 同一个 Research Object 在两个过程分别使用，建立两个 occurrence；它们可以值不同。设备跨多个过程使用也可多次引用。这样不会把“一次 10 g”默默算成两个过程各 10 g。

若未来确有一次 occurrence 同时属于多个执行的需求，再引入明确的共享 usage 身份；不要先用 many-to-many 关系复制实际值而不定义其含义。

### 5.3 关联时迁移字段拥有权

- 未关联时，ObjectOccurrence 的 field snapshot/values 是权威。
- 关联后，一次命令把这份使用值写入稳定的 Execution binding；canonical 文档节点换成 binding_ref。界面仍在原位编辑，用户感知不到“搬字段”。
- 已关联时，属性修改更新 binding values，同时生成 ExecutionRevision、owner revision 和投影。
- 解除关联时，一次命令将当前值取回到文档，生成新的执行版本与文档版本；旧 binding 值在 ExecutionRevision 中保留。
- 如果影响受保护的产物或依赖，先返回具体影响，不通过解除关联绕过删除/更正规则。
- binding ID 必须稳定；不能继续每次更新无差别删除重建所有 binding rows。

也可以只让文档永远拥有 Object usage 值，把 binding 作为从文档生成的 projection；但这样 Execution 的实际 bindings 也依赖另一套文档写入口，且脱离文档的执行难以复用。为统一执行事实，采用上述按是否明确关联分配权威的方案。

### 5.4 Record context 与 producer

当前 Sample/Data 作为 authoring record，说明这些执行被记在该上下文中，不自动说明它是每次执行的 input/output。

Process 菜单可提供“产出当前样品”或“产出当前数据”，显式建立 output binding。Data 保持一个 canonical producer；多个获取过程不全部设为 producer。Sample 有多个处理步骤时同样不自动改写最后一步的 product。

一个执行产出多个 Data/Sample 的既有能力保留；从其他记录查看时用只读版本引用，编辑入口回到唯一来源记录。

## 6. 插入、替换、复制、删除和历史更正

### 6.1 ID 与事实生命周期

| 操作 | occurrence/execution | 科研事实变化 |
| --- | --- | --- |
| 插入 `/Process` | 立即分配本地 occurrence ID，保存时建立 execution | 保存前只是待提交记录；保存时声明实际执行 |
| 修改参数 | 保留两个 ID，生成新 revision | 实际参数更正 |
| 同文档移动 | 保留两个 ID | 保存时更正流程顺序 |
| 同文档复制/跨记录复制 | 新 occurrence ID、新 execution 身份 | 新的待提交执行记录，不能复用旧执行 |
| 可确定的同文档剪切移动 | 保留 ID | 按移动处理；不确定则按复制 |
| 同模板换版本 | 保留 execution ID，显式选择新 Definition Version | 同一次执行记录更正，保留历史模板 |
| 替换 Process Definition | 保留 ID，清晰记录前后模板/值 | 无依赖时可更正；有依赖时走受保护更正，不能默默变成另一次事件 |
| 删除后本地 Undo | 恢复原 ID | 未保存则无数据库副作用 |
| 已保存更正后再 Undo+Save | 同一身份的新 revision | 不撤销历史审计 |

“替换本次记录的过程类型”与“新增另一次过程”不同。后者必须新建 occurrence；不能把同一个 execution ID 用于两次实际事件。

### 6.2 复制与批量：草稿不冒充已发生事件

“保存并再建一份”先保存原记录，再打开未持久化的新 Sample 草稿。复制正文、引用目标与字段值，但重新分配 block/occurrence IDs，清除 execution IDs、binding IDs、外部事实关联、完成状态和实际时间。

内部 Process/Object 关联可以作为**草稿关系意图**保留，并重映射到新 occurrence IDs；这不是复制旧执行事实。复制源记录的 output、Data inputs、source View、lineage 不能随之保留为已经成立的外部依据。

第二份第一次正常“保存记录”时才创建新的 Execution，表示用户提交新的实际记录。界面需要明确该按钮是在保存实际记录；刚复制出来、关闭或继续填写都不产生服务端真实执行。

如果以后要保存“尚未实施的计划”，必须有显式草稿/计划语义，不能让同一个 Save 在无提示的情况下有时代表计划、有时代表已经发生。当前首版不增设计划执行系统。

批量提交同理：临时表是草稿，提交是一次对多条实际记录的声明。固定 source revision、有界行数、client_row_id、完整 ID remap、整批事务与幂等；不复制 Data、附件、Experiment membership、View/Claim 或 lineage。编号仅在首次保存时分配。正文中的旧观察由用户检查，不做自动事实解析。

### 6.3 删除不能等同于 cancel

`cancel` 是执行被取消/中断；`retracted` 是此前记录需要撤回。两者分开，已完成执行不能因正文 Delete 就被说成“当时被取消”。

采用明确的首版规则：

| 状态 | 删除 ProcessOccurrence 后保存的行为 |
| --- | --- |
| 从未保存的本地 occurrence | 直接移除，不产生 execution/revision |
| 已保存、只有本记录管理的顺序与内部关联、没有外部科学依赖 | 从当前文档移除，并标记 execution record retracted；保留历史，不物理删除 |
| 具有 Data/Sample output、外部 lineage、外部固定版本引用或外部明确顺序依赖 | 普通删除被阻止，返回具体依赖；允许恢复 Ref 或进入记录更正操作 |

本记录自己的旧 revision 不算“外部依赖”，否则所有保存过的 occurrence 都无法删除。外部依赖包括其他记录固定的 execution/owner revision，也包括受影响的 View/Claim manifest。

受保护参数更正仍可生成新 ExecutionRevision；已有 Data/View/Claim 保持所用旧版本，不自动更新输入或历史依据。涉及撤回产物来源、改 output 或去掉实际依据的更正必须显式处理依赖，普通 Delete 不承担这种工作。

用户按 Delete 的两阶段选中/删除、随后 Undo 都先作用于本地草稿；保存时做最终依赖验证。可预先显示已知保护标记减少返工，不要求每次键击确认。

删除绑定的 ObjectOccurrence 也必须检查它是否在更改已生效的 execution input/output。受保护场景返回具体原因，不能只清掉正文而保留一个不可见且仍生效的 binding。

删除无外部依赖的 Process、而正文仍保留与它关联的 ObjectOccurrences 时，同一命令解除这些本记录内部关联，把使用值转回文档权威；保留 Object occurrence IDs 和值。旧 bindings 随执行版本留在历史中，不能让当前文档节点指向已撤回执行的活动 binding。保存差异展示这项连带更正，不额外制造多轮确认。

## 7. Data subject、输入版本与保存协议

### 7.1 多种 subject 依据共存

采用 DataSubjectAssignment 或等价 typed 结构，分别记录 manual 与 acquisition_document 依据。文档依据只能来自已确认 subject role 的 ObjectOccurrence；若已关联 binding，则从该稳定 binding 的 subject 语义取得依据。

```text
Data.subject = 去重(
  manual assignments
  ∪ 获取文档中的明确 subject 依据
  ∪ canonical producer 的 subject bindings
)
```

从 Sample 内创建 Data，当前 Sample 直接形成 manual assignment；没有 Process 也成立。tag 只建议 role，Equipment 可以成为 subject。移除一个来源依据不删除其他来源依据。

`derived_from` 仍来自 producer 的明确 input Data，不从正文位置、附件名或记录顺序推断。新服务统一维护 system relations，现有 `_sync_provenance` 不能在无 producer 时清空全部直接 subject。

### 7.2 精确版本与循环边界

明确 input/context 对象与 input Data 固定实际使用的版本；新的 Execution bindings 补版本 pin。未知实际时间保留未知，不用上传时间猜测。

Data 的 ObjectRevision 保存 acquisition document/sequence、subject 依据及对象版本、producer execution revision、input Data versions 和 Representation manifest。数据已经绑定了 E@r1 时，E 后续更正为 r2 不自动令 Data 漂移；显式更新数据来源才生成新的 Data revision。

对于**来自本 Data 获取文档的直接 subject 依据**，编辑并保存该 Data 记录时更新它的当前 subject manifest 与 revision；来自外部已固定执行/来源的依据仍保持原 pin。避免“所有 Execution 更新都自动刷新所有 downstream Data”造成传递双写。

如果用户正是在本 Data 的获取文档内更正其 producer，则这次聚合保存本身就是对该 Data 来源的明确更正：新的 Data revision 同时固定新的 producer revision，其他曾引用同一执行的 Data/View/Claim 仍保留原版本。普通修改执行的其他编辑入口也必须经过其唯一 authoring record 命令，不能绕过这一规则。

多种依据指向同一对象的不同版本时，manifest 保留各自版本和来源，不用最新版本覆盖；UI 可以按对象去重显示，详情保留版本差异。

output binding 连接产物 identity，不反向固定正在创建的产物新 revision。Sample 自己的 authoring context 也不要求 pin 同一事务尚未产生的 Sample revision，避免 owner revision → execution revision → owner revision 的循环。

旧数据没有保存过的 input/subject 版本标记为未固定，不在迁移时伪造历史。

### 7.3 Data Composer 固定保存链路

```text
begin draft -> upload files -> validate -> finalize metadata/document/executions -> Data ready
```

一次提交是一条用户明确组合的 Data identity。文字、照片、原始文件是同一记录的多个 Representations；不同测量事件应分别创建 Data。获取过程放 ScientificDocument，观察事实放 description Representation，简介不再复制同一份可编辑观察。

服务端保留可恢复草稿，附件有 client_attachment_id 和幂等映射；finalize 失败或响应丢失复用同一身份。部分上传失败需重试或明确移除，不能偷偷遗漏。已上传文件刷新可恢复，尚未上传的本地 File 需重新选择。

CSV/XLSX raw-first；解析是增强，不阻断原始保存。复用 preview/commit，保留 parser、mapping、checksum、原始行号与单位。解析失败显示“数据已保存，解析失败”。主 origin 明确选择，不能由上传完成顺序决定。

## 8. View 与 Claim 的固定版本语义

View 保存固定 Data versions + Representation 清单 + Artifact ID/hash + 必要 provenance。沿用 ViewState/ViewRevision 和 Asset，首版不另建独立 Artifact 业务身份。

- AI 实际读到 D@r1 就提交 r1；上传期间出现 r2 不改 pin。
- 修改 title/description 不 repin；更新来源/重新分析是显式动作。
- 历史 View 沿 manifest 读取不可变内容；Artifact 替换生成新 ViewRevision，旧文件可读。
- PNG/JPEG/PDF 优先；SVG 受限 image 预览，不注入 DOM；HTML 交互预览延期。
- 派生数值是新 Data，展示图/PDF 是 Artifact；外部分析 runtime 不内置。

Claim 分四项：`author_provenance`、typed `primary_source`、有界 `context_snapshot`、可选 `evidence`。保留现有作者 source_type/source_ref 的兼容语义，不将 Experiment/Data/View 塞入旧枚举。

| 来源位置 | 固定内容 |
| --- | --- |
| Experiment | Experiment revision、当时直接加入的 Sample/Data versions |
| Data | Data revision、该版本固定的 subjects |
| View | ViewRevision、其 Data versions、这些版本的 subjects |
| Experiment 内 Data/View Peek | 上述内容 + 明确的当前 Experiment revision |

Context 不递归整图、不自动生成 support evidence。编辑 statement 默认沿用原 Context；重新采集上下文才显式变更。Claim 标题自动取 statement 前缀；全局 Claim 页首版不提供无来源新建。

只存 Claim 朝外的 source/context；其他页面反查，不维护双向 claim_ids。Experiment Claim Tab 只按明确 source/context 实验关联取数据，不因为某个 Sample 被多个实验使用就把 Claim 到处分发。

## 9. Inline PropertySlot：第一目标与原型门禁

### 9.1 固定用户体验，不提前固定 DOM 实现

第一目标：`搅拌 60 ℃ · 30 min · 500 rpm` 在正文原位置直接输入，通过 Tab/Shift+Tab 切换字段，Escape 返回 Ref/正文，删除与撤销可预测。选中 Ref 展示全部字段 placeholder，未填字段不落空值，local 属性不修改默认模板。

“inline slot”是交互要求，不强制每个 slot 都必须是独立 ProseMirror 子节点。只要各字段身份、值、焦点、剪贴板和 undo 正确，原位原生 input 也是满足目标的一种实现，**不是弹出面板 fallback**。

### 9.2 已核查的锁定版本事实

本轮读取安装的 `@blocknote/react@0.54.0` 与对应源码：

- `ReactInlineContentSpec.tsx` 提供自定义 React NodeView、getPos、node、updateInlineContent、扩展注册入口。
- `content=none` 使用 atom，但默认 `selectable=false`，不能假定两次 ArrowLeft/Backspace 的整节点选中已自动实现。
- `updateInlineContent` 在该实现中通过 transaction replaceWith 更新整个 inline 节点。原型必须检查字段输入时是否引起 NodeView/焦点或 composition 重置；不能凭 API 名称认为是无副作用的属性更新。
- `propTypes.ts` 限制 props 为 string/number/boolean，动态 field payload 需要 codec。
- 底层 Tiptap NodeView 对节点内 input/textarea 的事件有隔离逻辑，但这不等于自动统一字段与正文 undo。
- styled inline 内容存在递归转换路径，不能武断断言嵌套 slots 不可能；其编辑边界仍需真实浏览器验证。

官方 [BlockNote Custom Inline Content](https://www.blocknotejs.org/docs/features/custom-schemas/custom-inline-content) 支持扩展入口与序列化基础。上述具体行为以本地锁定源码为准；**本轮是源码可行性检查，没有运行原型，不能宣称 IME/undo 已通过。**

### 9.3 原型候选 A/B

| 方案 | 实现 | 一致性/交互风险 | 结论 |
| --- | --- | --- | --- |
| A：原子 Ref + 原位置 slot inputs | 一个 Ref NodeView 内呈现有稳定 field ID 的原生输入，值通过编辑器 transaction 写回 draft | 需桥接字段 undo、焦点与 selection；原生输入便于 IME，需验证节点更新 | **优先原型** |
| B：Ref 内嵌可编辑 slot nodes | 每个字段由独立 inline 节点表达，编辑器管理文本 | 序列化、空节点、边界删除、嵌套 selection 风险更高；统一文本历史可能更自然 | A 不满足交互时评估 |
| Fallback：正文 inline 展示 + 紧邻属性编辑器 | 属性编辑离开正文原位置 | 交互目标降低，维护更简单 | 仅在明确门禁失败后使用 |

原型不接真实数据库、不做 Sample/Data 页面重构、不建设上传/表格；使用模拟 Definition/Object、加载保存 DTO、版本冲突响应和本地草稿即可。

测试文档至少包含两个相邻 Ref、同对象多次 occurrence、段首/段尾节点、空字段、local 属性和不同长度值。另有长文档压力样例，检查不为每个 Ref 挂独立 Query。

### 9.4 验证矩阵与失败标准

| 必测 | 通过要求 |
| --- | --- |
| 中文 IME/英文输入 | 不丢字、不重复提交、不提前打断 composition；IME Enter 不触发保存或选错候选 |
| Tab/Shift+Tab/Escape | 全字段可达，正文/Ref/slot 切换有稳定规则，无键盘陷阱 |
| ArrowLeft/Right、Backspace、Delete | 相邻 Ref、边界和最后一个字符行为稳定，不误删整个记录 |
| Undo/Redo | 字段、正文、binding、替换、删除与恢复形成一致历史，IDs 正确 |
| 内外复制/粘贴 | 内部保留结构并重映射身份；外部是可读文本，普通 `/`、`@` 不自动结构化 |
| 替换引用 | 相同字段身份才自动保留值，其余转 local，不猜同义字段 |
| 保存/恢复 | DTO round-trip 保真；响应不清空历史或覆盖保存期间的新输入 |
| Ghost preview | 不进持久化/undo 内容，不与 IME 竞争；候选切换不丢当前输入 |
| 浏览器与输入法 | 至少 Chromium、WebKit 自动化及 macOS 真实中文输入法手动验证；模拟 composition 测试不能替代真实 IME |

任一可复现的丢字、身份串用、字段/正文 undo 分叉、历史序列化丢值是阻断项。能通过受控扩展解决就继续保留 inline 目标；仅因开发量较大、首轮 demo 失败或样式未完成，不能判定 fallback。

fallback 门槛：记录最小复现与使用的锁定版本，完成针对 A/B 的可行性排查；仍存在核心交互阻断，或必须长期 fork BlockNote/维护第二个编辑内核才能满足要求。届时提交证据与具体体验差异，作为一次显式设计变更，不默默切换默认方案。

技术原型结果只决定 slot adapter 的实现或触发明确设计变更，不应改变 `/` 是实际执行、`@` 无隐式归属的已固定语义。

## 10. 页面、表格与创建流程：固定保留范围

| 范围 | 固定方案 |
| --- | --- |
| Research Object / Process Definition | 维护名称、tags、自身属性、默认使用字段及顺序；身份和字段 key 稳定，历史使用字段有快照 |
| Sample | 列表 + 连续 Editor；编号点击直接 Editor，轻量 Preview 为补充；支持历史只读模式 |
| Sample Data Composer | Sample 已有稳定 ID 后启用，数据不属于制备正文、不随 Sample 复制 |
| Sample 表格 | `required_refs` 行筛选与 `display_columns` 独立；默认编号/时间/记录对象 |
| Experiment 比较 | 使用同一 SampleTable，以成员为 scope，默认属性并集但 required_refs 为空 |
| 搜索 | 编号/名称或对象:属性[:值]；名称歧义解析成 ID，值在同 occurrence 匹配；搜索不重置列、筛选或 selection |
| 多值 | API 返回按 occurrence 顺序排列的数组，UI 用分隔符；第一非空值排序，空值与未引用区分 |
| 分页/排序 | 后端先全范围查询/排序再分页；不以当前页伪装全局结果；行 ID 稳定 |
| 手动行序 | 首版限定有界 Experiment 会话，作为展示状态；全项目任意手动序延期 |
| 列组/属性移动 | 组间、组内范围分开；hover/focus handle，提供非拖动替代 |
| Sample 多选添加到实验 | 菜单首项新建；加到已有实验留在 Sample 页并 toast，创建新实验立即跳转 |
| Experiment 列表新建 | Sample Picker → 选 Sample → 创建；自动标题 `YYYY-MM-DD HH:mm 实验`，详情 inline 改名 |
| 无 Sample | Picker 空状态提供创建 Sample 的可达入口，保留返回上下文；不提供显眼的空实验新建 |
| 空 Experiment 领域 | 允许存在，包括移除最后一个成员后的状态；不与“首版不提供入口”混淆 |
| Experiment refs | metadata patch、add/remove/reorder 分开；移出不删除目标，不自动加入所有关联 Data/subjects |
| Data | 独立获取正文 + 内容 Composer；动态表仅查 acquisition Process/Equipment，不跨查 Sample 配方 |
| Data/View/Claim Peek | 共用 Drawer 和各自 DetailBody，完整页稳定 URL；Back 关闭 Peek 并恢复来源状态 |
| Claim | 从 Experiment/Data/View 创建，statement 自动标题，source/context 反查，支持更正与归档 |

Picker selection 是独立 ID 集合，跨搜索/分页保留，显示隐藏已选数量；切项目清空。服务端提交时重验 scope/存在性，不以 UI 选择保证有效。

URL 由 nuqs + schema parser 保存 query/display 状态与版本，IDs 替代名称，限制长度，selection 默认不分享。URL 固定查询配置，不冻结结果集；分析结果通过 View/Claim pins 固定。

文本字段首版不做单位换算、数值 DSL、同义自动合并；旧 typed values/units 保留原结构，不能全量字符串化。local 字段有独立身份，默认不修改模板。Sample tag 中英文约定由同一领域服务识别，当前编号规则不由 UI 临时改写。

## 11. 服务边界、复杂度控制与兼容

### 11.1 前端与依赖

保留 `scientific-document / scientific-composer / sample / data / data-composer / experiment / view / claim / tables / peek / queries` 的边界。

ScientificComposer 只认识编辑 DTO、候选 provider、变更事件，不 import Sample/Data/Experiment API。页面容器决定保存上下文；领域命令承担原子性。过程绑定选择器是编辑器的领域能力，不是 StepForm。

服务端状态使用已有 React Query，URL 使用 nuqs，编辑历史使用 BlockNote，本地文件/批量草稿使用局部状态。表格采用受控状态，不引入第二套全局 store。Peek/完整页使用同一 DetailBody。

保留 BlockNote/Base UI/Query/nuqs/Zod；TanStack Table 作为首选候选，具体版本与 API 在原型/实施前锁定；dnd-kit 按保留的拖动功能引入；react-dropzone 只负责文件交互。不加入第二个富文本编辑器、图数据库、队列、React Flow、Notebook、重量级 uploader 或万能电子表格引擎。

### 11.2 改造范围

保留现有身份表、Definition/Version、Execution/Revision、Data/Representations/Import/Asset、Experiment、View/Claim 和 API/MCP 框架。

必要的变化集中于：

- 文档/草稿 codec、唯一编辑归属与稳定 occurrence 身份。
- occurrence 查询投影、带来源的 sequence 投影、稳定 binding IDs。
- 直接 subject 依据、输入 revision pins、Data/View/Claim 历史 manifests。
- 聚合事务、幂等占位、版本检查、可恢复提交与保护删除。
- 连续 Composer、动态表与各业务页面重构。

这比“文档只做 mention”的 v1.4 默认路线更复杂，但符合已明确的产品语义，且成本集中在一个文档聚合命令和编辑器适配器。禁止以每次击键立即分别写文档/Execution/Graph 的方式实现，也不建立双向自动同步后台。

### 11.3 旧 Sample/Execution 迁移

旧数据按实际已知事实转换，不根据 note 重新解释步骤。

- 现有 execution ID、Definition Version、实际字段、binding 快照和明确 Data/output 关系保留。
- 基于旧 Sample step 顺序生成稳定 ProcessOccurrences；转换 mapping 一次持久化，重试不随机换 ID。
- 旧 sequence 只有确认来源属于 Sample record 时才接管为 record_sequence；不把来源不明的显式边批量覆盖。
- 一个旧 Execution 若同时通过多个产物被不同 Sample projection 看到，先确定唯一编辑来源；其他记录只读引用。不能为适应新约束复制实际事件。
- 旧 `sample_record` context binding 可辅助确定归属，但 `authoring_record_id` 不等同于 input/output。
- 旧 completed/draft 状态保留；旧 draft 不因迁移就宣布实际发生。新正常 Save 声明实际事件时使用明确的 recorded/running/completed 语义；当前枚举需支持“已记录发生、完成情况未说明”，不能强行填 completed 时间。
- 旧值未 pin 的历史版本标记缺失，不用最新对象伪造。
- 初次切换建立新的 owner revision 和 manifest，旧 revisions 不重写。记录转换完成后，所有可编辑路径统一进入聚合命令。

### 11.4 可靠性硬条件

命令拥有外层事务；内部服务只 validate/flush。并发 token 使用被编辑聚合自己的版本，不用包含实时关联列表的动态 hash 代替。锁保护内重验，幂等 key/业务结果/ChangeSet applied 原子提交。

附件 bytes 与数据库不可假装同一事务；上传 staging 与 finalize 分开。历史引用资产保留，日常科学对象默认归档。JSON manifest 中的 IDs 需要 deletion service/引用索引保护，不能仅依赖数据库当前 FK。

涉及实际执行事实的撤回、producer 更正与外部引用保护在服务端强制，不由各页面各写一套条件。

## 12. 冻结验收与未验证事项

下列是未来实现应满足的条件，本轮没有把源码检查当作运行验证：

1. 无 Process 的 Sample/Data 可保存；有 `/Process` 时，保存创建实际 Execution，无需二次创建。
2. `/搅拌 60 ℃` 修改为 80 ℃：current Execution、current 文档、表格一致；旧记录版本仍显示 60 ℃。
3. `E1,E2,E3` 改为 `E3,E1,E2`：文档与 record_sequence 原子变化；外部显式边不被删除，冲突返回明确错误。
4. 移动 `@乙醇` 到另一个 Process 附近不改变 binding；明确菜单关联才改变使用关系。
5. 已关联 Object 属性从 inline 修改：稳定 binding ID，执行与表格一致；取消关联回到文档权威而不丢值。
6. 新建 Ref→删除→Undo、已保存→修改→Undo→Save、内部复制多次，都不串 occurrence/execution/binding 身份。
7. 复制/批量草稿在提交前不建立实际 Execution，不复制旧 Data/外部 lineage；首次保存才分配新对象编号。
8. 有外部产物依赖的 Process Delete 不产生半保存；未保护执行撤回可查历史，未误设 cancelled。
9. REST/MCP 改文档管理的 Execution，与 UI 使用同一版本检查、事务、projection 和 revision。
10. Data 无 Process subject、多依据 subject、raw-first、多文件失败恢复与响应丢失重试正确。
11. View/Claim 历史能读到对应 Data、执行版本、Representation 和 Artifact；当前更正不改变旧 manifest。
12. 实验异构配方默认比较不丢行；分页、排序、隐藏 selection、Picker 返回上下文和空状态可用。
13. 真实中文 IME 与正文内 slot、统一 Undo、剪贴板和序列化通过第 9 节门禁。
14. 旧 Sample 执行身份、共享产物、历史状态、lineage 与已固定版本不丢失。

产品语义和上述边界按本版固定。尚未冻结的是 slot adapter 的具体实现、实际数据规模预算、索引物理形态及依赖精确版本；这些应由原型和实现验证决定，不能在没有证据时宣布已解决。原型失败若需改变 inline 用户体验，走明确设计修订；不自动启用 fallback。
