# 科研工作台核心工作流完整产品与技术设计方案 v1.3

## 0. 文档定位

本文定义科研工作台下一阶段核心工作流的产品设计与技术设计边界，覆盖：

- Research Object；
- Scientific Composer；
- Sample；
- Sample 列表与比较；
- Experiment；
- Data；
- Data Composer；
- View；
- Claim；
- 各对象之间的引用关系；
- 页面跳转关系；
- 可复用的前端能力；
- 现有仓库可以直接复用的代码；
- 推荐评估的开源项目；
- 已知与当前实现存在冲突、需要后续 Coding Plan 决定的架构问题。

本文不是 Coding Plan。

本文不规定：

- migration 执行顺序；
- PR 数量；
- milestone；
- 每一步具体修改哪些文件；
- 数据库具体 SQL；
- 最终 API endpoint 命名。

这些应在 Astra 对本文和完整仓库审查完成、产品设计进一步讨论确认后，再形成 Coding Plan。

# 1. 整体产品目标

科研工作台不应该变成一个传统 ELN/LIMS 式的大量表单集合。

它应该围绕三个最基本的科研动作建立：

> **Scientific Composer：记录怎么做。**

> **Data Composer：记录得到了什么。**

> **Claim Composer：记录从这些事实中得出了什么判断。**

Sample、Experiment、Data、View 是这些动作发生的上下文。

整体关系可以理解为：

```text
Research Object
        │
        ▼
Scientific Composer
        │
        ├── Sample 的制备/处理记录
        └── Data 的获取/测试过程
        

Data Composer
        │
        └── Data
             ├── 文本描述
             ├── 表格
             ├── 图片
             ├── 原始文件
             └── 其他 Representation
                    │
                    ▼
                   View
                    │
                    ▼
                  Claim


Experiment
├── Sample
├── Data
├── View
└── 通过反向查询看到 Claim
```

产品核心原则：

> **自然语言是输入界面，结构化引用是确定性数据，Research Graph 是长期数据本体。**

# 2. 核心领域原则

## 2.1 Research Object

原料、设备、Sample 等不继续依赖僵硬的类别层级。

统一建立在 Research Object 基础上，通过：

- tag；
- 名称；
- 自身属性；

进行区分。

Research Object 至少具有：

```text
id
code / number
name
tags
properties
process properties
```

### 自身属性

描述这个对象本身。

例如：

```text
2-POA

CAS: 2688-84-8
纯度: 98%
供应商: XXX
批次: B240901
```

或者：

```text
气敏测试台

型号: GS-03
厂家: XXX
最大流量: ...
```

### Process / Usage Property

表示它在一次具体使用中需要填写什么。

例如 2-POA：

```text
用量
浓度
加入方式
```

设备：

```text
转速
设定温度
气体流量
```

这些值不属于 Object 本体，而属于具体 occurrence。

---

## 2.2 同名对象

如果两个对象名称相同，但：

- 批次不同；
- 型号不同；
- 性能不同；
- 来源不同；

除了在自身属性中保存差异，还建议直接在名称中体现关键区别。

例如：

```text
2-POA｜批次 B240901
2-POA｜批次 B240915
```

或者：

```text
碳纸｜Toray TGP-H-060
碳纸｜自制 055
```

原因是名称会直接出现在：

- `@` 搜索；
- Sample 表；
- Data 表；
- AI 查询结果；
- Experiment；
- Claim Context。

名称首先需要做到人可区分。

# 3. Scientific Composer

## 3.1 定义

Scientific Composer 是 Sample Editor 和 Data Acquisition Editor 共享的核心编辑器。

它负责：

> **记录过程，以及过程里明确出现的科研对象。**

它不是一个 Step Form。

也不是一堆 Process Card。

它是一篇连续科研正文。

---

## 3.2 基础文档模型

概念模型：

```text
ScientificDocument
├── Text
├── ProcessRef
└── ObjectRef
```

其中：

```text
ProcessRef
├── reference
├── occurrence_id
└── property values
```

```text
ObjectRef
├── reference
├── occurrence_id
└── property values
```

同一个对象可以在同一文档出现任意多次。

每一次 occurrence 都独立。

---

## 3.3 不建立 StepBlock

不建设：

```text
StepBlock
  ├── Process
  ├── Object
  └── Paragraphs
```

也不建立：

```text
Process owns following paragraphs
```

或者：

```text
Object belongs to nearest Process
```

用户视觉上可以按步骤写：

```text
/配液
@2-POA 10 g 与 @乙醇 90 g 混合。
持续搅拌至体系变白。

/浸渍
将 @原纸 通过 @卷对卷设备 完成浸渍。
```

但这是写作形式。

不是数据库强制关系。

---

# 4. `/` 与 `@`

## 4.1 `/`

```text
/
```

用于：

> Process。

例如：

```text
/搅拌
/浸渍
/SEM 测试
/氯气响应测试
```

---

## 4.2 `@`

```text
@
```

用于：

> 当前 Scientific Composer 中允许引用的 Research Object。

例如：

```text
@2-POA
@乙醇
@Sample-A
@磁力搅拌器
```

第一版不让 `@claim`、`@data` 等特殊字符串承担：

> 「创建一个新 Claim / Data」

这种完全不同的语义。

即：

> `@` 负责引用，不负责创建特殊业务对象。

Data 和 Claim 使用独立 Composer 创建。

未来如果确实需要在正文中引用已有 Data，可以再单独讨论稳定且不产生歧义的引用形式。


## 7.2 空属性

## 7.3 新增属性



## 7.4 occurrence-local

编辑器中临时新增的属性默认：

> 只属于当前 occurrence。

不会偷偷修改 Process / Research Object 的默认 schema。

以后可以显式提供：

> 保存为默认属性。

# 8. 属性 v1 数据类型

第一版全部采用文本：

```text
温度 = "60 ℃"
时间 = "30 min"
转速 = "500 rpm"
固液比 = "1:10"
型号 = "HPMC-400"
pH = "7.2"
```

不做：

- number；
- quantity；
- unit conversion；
- range；
- formula；
- boolean；
- select；

等复杂 typed property UX。

未来出现真正：

- 数值统计；
- 单位换算；
- 范围查询；
- 自动绘图；

需求后再升级。

# 18. Scientific Composer 不能把 UI 结构等同于后端 Step

这是当前方案最需要 Astra 审查的架构问题之一。

当前 Sample API 仍然要求：

```text
steps: list[SampleRecordStepDraft]
```

而且 `SampleRecordCreate.steps` 当前要求至少一个 step。

当前 Sample Record Service 也围绕 ProcessExecution 序列保存 Sample。

这和新的产品语义存在明显冲突：

> ScientificDocument 可以完全没有 Process。

例如：

```text
今天复测发现样品表面轻微变色。
```

合法。

或者只有：

```text
@Sample-A 在室温下放置 24 h。
```

同样合法。

因此后续 Coding Plan 必须解决：

> 编辑器连续文档和当前 Step / ProcessExecution projection 如何对齐。

但产品层面已经确定以下要求：

1. 每个 Ref 必须具有稳定 occurrence ID；
2. occurrence property 不能依赖解析正文获得；
3. 文档即使没有 Process 也必须合法；
4. ObjectRef 不必须属于 Process；
5. ProcessRef / ObjectRef 必须能够被 Sample/Data 表查询；
6. UI 不允许因为当前后端是 step 模型，就重新强迫用户使用 StepBlock。

Astra 应重点审查：

> 是否继续以 ProcessExecution 作为可查询 projection，还是需要更通用的 ScientificDocument Reference persistence。

这属于 Coding Plan 前必须解决的架构点。

```text

```

---

# 22. 保存并再建一份

适合连续创建少量类似 Sample。

保存当前 Sample 后：

1. 创建新的独立 Sample；
2. 复制当前 ScientificDocument；
3. 复制 ProcessRef；
4. 复制 ObjectRef；
5. 复制 occurrence properties；
6. 复制正文；
7. 新 Sample 获得新编号；
8. 用户直接修改。

不创建：

```text
parent
child
variant
derived_from
```

等复制关系。

---

# 23. Data 不跟随 Sample 复制

这是硬规则。

无论：

```text
保存并再建一份
```

还是：

```text
保存并批量写入类似样品
```

都不复制：

- Data；
- Observation；
- 已上传照片；
- 已上传测试文件；
- Data Composer 输入内容。

原则：

> **可以复制准备怎么做，不能复制实际发生过什么。**

# 71. Experiment 当前 API 风险

当前 `updateExperimentRecord` 采用：

> replacement semantics。

即一次更新会重建全部 references。

而新的产品 UX 会大量发生：

```text
添加 Sample
添加 Data
添加 View
```

因此 Astra 必须检查：

> 后续是否应该提供增量 reference mutation，或者客户端必须安全 merge 后再 PUT。

不能出现：

> 添加一个 Sample 时意外删除已有 Data/View 引用。

这属于后续 Coding Plan 需要明确的 API 语义问题。

# 72. Data 的定义

Data 表示：

> 一个科学事实或测量结果的 identity。

同一个 Data 可以具有多个 Representation。

例如：

```text
Data: Cl₂ 响应测试 0905

Representation A:
仪器原始 CSV

Representation B:
解析后的 Table

Representation C:
测试现场图片

Representation D:
文本观察
```

---

# 73. Observation

制备过程中的事实性观察，例如：

```text
溶液逐渐变为乳白色。
```

```text
样品在 50 ppm Cl₂ 下约 15 s 后由淡黄色转为棕黄色。
```

可以作为：

> description/text Data。

因此：

> Observation 属于事实层，可以以 Data Representation 形式保存。

Claim 则是解释层。

# 81. Data Subject

`@Sample`、`@原料` 等可以表明：

> 被测试对象。

默认：

- Sample / Material 类对象优先推断为 subject；
- Equipment 类对象优先推断为 acquisition equipment。

但需要承认一个边界：

> 设备本身也可能成为测试对象。

> 对 Ref role 进行人工覆盖的能力。

例如菜单：

```text

作为测试设备
```

第一版可以仅在出现歧义时暴露。

- 图表编辑器；
- Prism 替代品；
- Excel 替代品；
- 曲线拟合工作台；

- Python；

# 100. AI 创建 View

这是外部 AI 非常适合的能力。

例如用户：

AI 可以：

1. 读取 Experiment；
2. 读取相关 Samples；
3. 读取 Data；
4. 必要时创建 Derived Data；
5. 做分析；
6. 生成图表；
7. 创建 View；
8. 让 View 引用相关 Data；
9. 上传展示 Artifact；
10. optionally 创建 Claim。

Workspace 不需要内置同等分析能力。

# 125. Table 技术候选：TanStack Table

当前仓库尚未依赖 TanStack Table。

建议 Astra 重点评估：

> `@tanstack/react-table`

而不是手写所有 Table state。

原因是我们的需求已经包括：

- dynamic columns；
- grouped header；
- controlled sorting；
- row selection；
- column order；
- visibility；
- filtered row model。

TanStack Table 是 headless table library，逻辑与视觉分开，适合保留当前低对比、自定义 UI。官方提供 sorting、selection、column ordering 等状态能力。

推荐：

```text
TanStack Table
负责：
- rows
- columns
- header groups
- sort
- selection
- visibility
- column state

我们的代码
负责：
- scientific filter semantics
- two-row visual
- sticky
- occurrence aggregation
- styling
```
